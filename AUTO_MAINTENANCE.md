# Automatic refresh and bounded recovery

- No Codex heartbeat or local computer is required. Existing GitHub Actions and the deployed Worker perform checks. GitHub schedules can be delayed; this is not a tick-level SLA.
- Comparison Monitor runs every 15 minutes. Existing domestic spot/FX/identity checks remain intact. Binance and Bybit futures now test the same public WebSocket paths used by the browser, requiring current prices for BTC, ETH and SOL. Coinbase tests the current authenticated bulk gateway cache. These source checks are not an exhaustive price reconciliation of every futures contract.
- The authenticated resources probe warms the shared L1/L2 fee and news caches and checks their actual successful refresh times. It also checks the market snapshot, DeFi and APYWA component health. Publication dates of news articles or 24-hour fee aggregation windows are not incorrectly treated as transport failure.
- Ordinary snapshot rebuilding, bounded retries, existing verified fallback paths and the refresh watchdog remain responsible for rebuilding and republishing market/DeFi/rating data. Browser stream watchdogs now detect stalled Binance and Bybit futures as well as Coinbase. Late/future/out-of-order source ticks are rejected for all three.
- News refreshes are coalesced; failures retain the last successful data and enforce a shared 60-second cooldown. Failed attempts never advance the original data timestamp.
- Detailed monitoring results and recovery transitions are stored in the existing private refresh history, which requires the administrator password again. A persistent failure alerts only after at least three checks spanning 30 minutes and is deduplicated until recovery. Public CI output contains aggregate counts, not private records.
- The release guard uses a same-origin HEAD request roughly every 10 minutes, with a second observation a minute later before a release reload. No full HTML download is used to check versions. It preserves the current route and reloads a given release at most once per tab. It skips hidden/offline tabs, login, board/news views, focused inputs and open dialogs. A deferred reload is retried after the protected interaction ends. Existing already-open code needs one reload to install this guard.
- No automatic arbitrary code edits, unverified API migrations, fabricated prices, login bypass, or paid feed is introduced. A permanently retired endpoint, upstream permission change or unavailable provider can still require a reviewed code change. Daily audit PDFs remain dated reports, not invented live holdings.
- The refresh watchdog pins GitHub's documented API version. After a transient dispatch error it checks whether the requested run already exists; ambiguous outcomes are left for the next scheduled check, never blindly redispatched or labeled as successfully repaired.

Tests: `node --test test_app_update.cjs test_futures_health.mjs test_comparison_health.cjs comparison-identity.test.cjs server-auth/board-permissions.test.mjs server-auth/security-regression.test.mjs`; existing browser regressions remain required.

- Confirmed incidents remain latched through gaps in monitoring until an actual healthy observation. An unconfirmed streak still resets after a gap, so missed observations cannot fabricate a new persistent failure. Zero newly active alerts does not mean every comparison is healthy; inspect the delayed/identity counts too.

Existing 24-hour expiry and current native-quote requirements remain unchanged.
- Existing market, board, uploads, links, Korean search, charts, futures, issue caches and login regressions remain required. Tests do not modify real posts, memberships or uploads. Real-device Safari/iOS and an exhaustive penetration/load test remain outside this audit.
- GitHub scheduled jobs can still be delayed by the hosting platform. Persistent provider restrictions are kept visible in the private administrator history; successful workflow completion alone must not be presented as proof that every source recovered.

## 2026-11-23 Delivery Architecture Comparison

- Public reference inspected: https://www.trackify.kr/soop/khm11903 . A normal Chrome visit returned 200. Observed page APIs were split into small batch/trend/broadcast/event requests (about 71 bytes to 11.5 KB for the sampled content responses), with a separate WebSocket subscription path. Hashed JavaScript/CSS assets advertised `public, max-age=2592000, immutable`; the chart bundle was requested later. This establishes observable client delivery behavior, not its private database design, backend capacity or visitor count. One local cold visit had first contentful paint around 1.74 seconds; this is not a universal speed guarantee.
- Our initial authenticated load instead requested the complete snapshot, including all futures, descriptions, DeFi and audit material. The last observed published storage payload was 6,446,095 bytes, which is not a compressed on-wire measurement. A local archived sample measured 4,274,936 bytes after ordinary-user redaction and 1,721,510 bytes for the new market scope (about 60% smaller, without comparison bootstrap). These sample sizes are not claimed as current production response sizes or end-user timings.
- Authenticated snapshots now support market/futures/ranking/audit/search scopes. They retain every spot row needed for client sorting/comparison plus canonical names, listing/risk flags and contract/explorer identity evidence. Hidden descriptions and unrelated resource datasets are omitted. A matching `baseSince` receives only the additional section; mismatched generations receive a complete shared base. Client validation refuses a section from another generation.
- Coin introductions have a separate authenticated, symbol-validated endpoint. A modal or intentional hover/focus can fetch that small record without waiting for a complete snapshot. Existing complete descriptions remain visible while their source revision is revalidated. Verified missing records, failed transport and pending metadata remain distinct. Full description search lazily requests the search scope, so it does not silently become name-only search.
- Complete cached views use their embedded immutable server revision for not-modified checks; mutable live tick clocks and the old separate cache marker cannot skip missing sections. Scope upgrades bypass not-modified when the required section is absent, and same-generation merges preserve already acquired views. A new generation retires old resource sections rather than relabeling them as fresh.
- The Worker coalesces concurrent snapshot reads and keeps one decoded snapshot behind a storage revision check. Atomic chunk transactions are unchanged; every publication gets a new revision, including same-generation retries. API usage accounting moves behind `waitUntil` through a serial queue, so metrics writes do not hold the response. Authentication, no-store responses, password verification and source freshness rules are unchanged.
- Logo rendering now indexes symbols once per render instead of repeatedly flattening and scanning all exchange lists for every visible coin. Browser regressions bound the symbol lookups for 50 logos, in addition to scoped transfers, independent introductions, description search, reload metadata and rapid resource navigation.
- Deployment probes now report production delivery byte counts and warm snapshot-read duration as aggregates only. This probe remains GitHub-OIDC-only, reveals no snapshots or private records, and is not an end-user load-time SLA. Existing free services and schedules are retained; no paid feed or background Codex automation was added.
- Deployment verification additionally accounts for Cloudflare's [default five-minute deferred Durable Object code update](https://developers.cloudflare.com/durable-objects/deployments/durable-objects-code-updates/), introduced on 2026-10-30. The new delivery-version probe waits within a bounded window using 15-second checks, instead of misclassifying the former one-minute observation window. The default in-flight-request protection is retained, not replaced by a forced immediate reset. These deployment minutes are not page-load latency seconds.
- Production follow-up at 2026-11-23 14:46 UTC (deployment job 137772056638) confirmed `deliveryVersion: 1`: ordinary full JSON plus cached comparison bootstrap was 5,865,505 bytes; the market scope plus the same bootstrap was 3,006,853 bytes (49% smaller). Additional sections were 1,449,298 bytes for futures, 389,014 for ranking, 497,832 for audit and 1,500,122 for text search, including bootstrap in each measurement. BTC introduction was 3,546 bytes. These are actual server-side serialized JSON byte counts, not compressed network sizes or a claimed percentage reduction in user-perceived load time.

## 2026-11-24 Telegram Burst Catch-Up

- The initial latest-preview-only collector above is superseded. Each channel now retains a committed message-ID watermark and a separate unfinished catch-up boundary. Older pages are requested with an exclusive `before` ID until the previous watermark is crossed. Message IDs are compared as decimal BigInts, not rounded JavaScript Numbers; missing integer IDs are not mistaken for missing posts because deletions and service/media messages can create legitimate gaps.
- Each invocation processes at most two pages per channel, with the existing three-source concurrency limit. This is an invocation budget, not a permanent history cap: unfinished target/boundary state persists and resumes through the already-existing minute trigger. Quiet completed channels stay on their ten-minute polling schedule. No additional scheduled workflow, local process, bot credential or Codex task is required.
- A moving live head cannot move the target of an in-progress batch. After catch-up completes, the channel is queued for an early head recheck to collect posts that arrived during recovery. Deployment of this change migrates the previous last-success time into a timestamp boundary without discarding an unseen interval. A completely new source still initializes from its current preview, rather than importing its entire past history.
- Media-only records remain pagination boundaries even though they do not become text issues. Empty, malformed, duplicated, future-dated or nondecreasing older pages are failures, not successful empty history. A page-size safety bound throws explicitly instead of silently truncating the input. Transport failures preserve the last good cursor/boundary and use bounded exponential backoff; the minute continuation route is internal-only and cannot be invoked by an anonymous visitor.
- Issue writes finish before checkpoints are persisted. A write failure or restart before checkpoint commit replays the page idempotently. Successful partial pages can persist a continuation boundary after a later HTTP failure, while the committed high-water mark and last-complete-success time remain unchanged. Pending catch-up is not reported as a fully healthy source in the existing private monitor.
- Added regressions simulate a 100-ID burst with media-only pages and a moving head, process restart, minute-trigger continuation independent of failed FX, partial HTTP failure, issue-write/cursor-commit failures, idempotent replay, legacy timestamp migration and malformed/stalled/empty older pages. The full Node suite now passes 142 checks. The native-selector browser parser regression also passes; real public pagination returned 19 older records for `BChoSN?before=33995`, all strictly below that boundary.
- Collection coverage and display retention are distinct. The existing per-coin latest-50 Telegram excerpt archive and latest-50 Coinness archive remain bounded; this change does not promise unlimited historical storage. Public-preview pagination is still not a guarantee of recovering posts deleted before collection, private/restricted posts, source outages or arbitrary upstream layout changes. Those limitations must not be described as a guarantee of zero loss.
- Native production verification at 2026-11-23 16:09 UTC (2026-11-24 KST, deployment job 137826922313) confirmed `telegramVersion: 3`, seven committed channel cursors, no pending/error states, 135 preview records and 35 matched records. The independent market comparison monitor still reported outstanding provider/identity alerts and woke the existing watchdog; this Telegram verification is not a claim that every market source is healthy.

- A one-time bounded migration restores old excerpts from exact public message IDs, with up to three source-page requests per repair pass on the existing minute schedule. One page can restore multiple retained posts; round-robin progression prevents an unavailable older post from starving other records. Concurrent administrator deletion cannot resurrect a record during restoration.
- Immutable bodies publish before their metadata references. Body-write failure cannot advance the source cursor or remove the previous article. Encrypted backups include full bodies and the migration state through the existing coin-content namespace.

Telegram source labels distinguish original text from any older excerpt that has not yet been restored.
